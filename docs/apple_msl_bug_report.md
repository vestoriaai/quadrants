# Apple bug report (ready to file)

**Title:** Metal Shading Language compiler silently drops updates from a conditional read-modify-write of a buffer element inside a loop (loop-carried memory dependence ignored)

**Area:** Metal | Shading language compiler (metal / `newLibraryWithSource`)

---

## Environment

| Item | Value |
|---|---|
| Machine | `Mac16,10` — Apple M4 (10-core GPU, Metal 4) |
| OS | macOS 26.5 (25F71), Darwin 25.5.0 |
| Xcode | Xcode 26.6 (Build 17F113) |
| Metal compiler | `xcrun -sdk macosx metal --version` → `Apple metal version 32023.883 (metalfe-32023.883)`, default target `air64-apple-darwin25.5.0` (Metal.xctoolchain 17.6.109.0) |
| Kernel compilation | at runtime, `-[MTLDevice newLibraryWithSource:options:error:]`, default `MTLCompileOptions` |
| Dispatch | 1 threadgroup × 1 thread (no cross-thread races possible) |

## Summary

A compute kernel that performs a **conditional read-modify-write of the same device-buffer element inside a runtime loop** loses all but the last update. Each loop iteration appears to read the element's **pre-loop** value — as if the load were hoisted/GVN'd across the loop-carried memory dependence — so only the final store survives. The same code without the `if`, or executed on the CPU, is correct.

The kernel below is machine-generated by our compiler stack (hence SPIR-V-Cross-style names) but was hand-verified line by line: the load of the accumulator is inside the branch, inside the loop body, and the store targets the same device address. The failure is therefore in the Metal source → GPU compilation pipeline, not in the MSL we feed it.

## Minimal reproduction

### 1. Compute kernel — save as `/tmp/a5.msl`

```msl
#include <metal_stdlib>
#include <simd/simd.h>

using namespace metal;

struct _16
{
    int _m0;
};

struct _17
{
    _16 _m0;
    char _m1_pad[8];
    ulong _m1;
};

struct args_t
{
    _17 _m0;
    char _m1_pad[8];
    _17 _m1;
};

constant uint3 gl_WorkGroupSize [[maybe_unused]] = uint3(1u);

kernel void main0(constant args_t& args [[buffer(0)]], uint3 gl_GlobalInvocationID [[thread_position_in_grid]])
{
    if (gl_GlobalInvocationID.x == 0u)
    {
        for (int tmp5_i32 = 0; tmp5_i32 < args._m0._m0._m0; tmp5_i32++)
        {
            float tmp11_f32 = (reinterpret_cast<device float*>(args._m0._m1))[int(uint(tmp5_i32 << 2) >> uint(2))];
            if ((tmp11_f32 >= 0.0) != false)
            {
                float tmp18_f32 = (reinterpret_cast<device float*>(args._m1._m1))[0];
                float tmp19_f32 = (reinterpret_cast<device float*>(args._m0._m1))[int(uint(tmp5_i32 << 2) >> uint(2))];
                (reinterpret_cast<device float*>(args._m1._m1))[0] = tmp18_f32 + tmp19_f32;
            }
            else
            {
            }
        }
    }
}
```

Semantics: `acc = 0; for i in 0..n-1: if xs[i] >= 0: acc = acc + xs[i];` — i.e. sum the non-negative elements of `xs`.

### 2. Host harness — save as `a5_runner.m` (Objective-C, same directory)

```objc
// A5 decisive experiment: run the dumped (semantically-correct) MSL standalone on Metal.
// If this prints 6.0 -> our own compiler path diverges from the dumped MSL.
// If this prints 4.0 -> Apple's MSL->GPU toolchain miscompiles correct MSL.
// Build: clang a5_runner.m -o a5_runner -framework Metal -framework Foundation
#import <Metal/Metal.h>
#import <Foundation/Foundation.h>
#include <stdio.h>

int main(int argc, char **argv) {
    id<MTLDevice> device = MTLCreateSystemDefaultDevice();
    NSString *src = [NSString stringWithContentsOfFile:@"/tmp/a5.msl" encoding:NSUTF8StringEncoding error:nil];

    MTLCompileOptions *opts = [[MTLCompileOptions alloc] init];
    NSError *err = nil;
    id<MTLLibrary> lib = [device newLibraryWithSource:src options:opts error:&err];
    if (!lib) { printf("compile error: %s\n", err.localizedDescription.UTF8String); return 2; }
    id<MTLFunction> fn = [lib newFunctionWithName:@"main0"];
    id<MTLCommandQueue> q = [device newCommandQueue];
    id<MTLCommandBuffer> cb = [q commandBuffer];
    id<MTLComputeCommandEncoder> enc = [cb computeCommandEncoder];

    float xs[4] = {-1.0f, 2.0f, -3.0f, 4.0f};
    int n = 4;
    float acc = 0.0f;
    id<MTLBuffer> bxs = [device newBufferWithBytes:xs length:sizeof(xs) options:MTLResourceStorageModeShared];
    id<MTLBuffer> bacc = [device newBufferWithBytes:&acc length:sizeof(float) options:MTLResourceStorageModeShared];

    // args_t layout (from MSL): { _17 _m0; pad[8]; _17 _m1; }, _17 = { _16 _m0(int); pad[8]; ulong _m1; }
    struct _16 { int32_t _m0; };
    struct _17 { struct _16 _m0; uint8_t _m1_pad[8]; uint64_t _m1; };   /* mirrors MSL: _m1 at offset 16, size 24 */
    struct args_t { struct _17 _m0; uint8_t _m1_pad[8]; struct _17 _m1; };  /* _m1 at offset 32 */
    _Static_assert(sizeof(struct _17) == 24, "layout");
    _Static_assert(sizeof(struct args_t) == 56, "layout");
    struct args_t a;
    memset(&a, 0, sizeof(a));
    a._m0._m0._m0 = n;  a._m0._m1 = bxs.gpuAddress;
    a._m1._m0._m0 = 1;  a._m1._m1 = bacc.gpuAddress;

    [enc setComputePipelineState:[device newComputePipelineStateWithFunction:fn error:&err]];
    [enc setBytes:&a length:sizeof(a) atIndex:0];
    [enc dispatchThreadgroups:MTLSizeMake(1,1,1) threadsPerThreadgroup:MTLSizeMake(1,1,1)];
    [enc endEncoding];
    [cb commit];
    [cb waitUntilCompleted];

    float *p = (float*)[bacc contents];
    printf("standalone Metal acc = %f (want 6.0)\n", p[0]);
    return 0;
}
```

Argument marshalling is covered by `_Static_assert` layout checks, so the failure is not an argument-binding artifact.

## Expected vs actual

- **Expected:** `standalone Metal acc = 6.000000 (want 6.0)` — the non-negative elements of `xs = {-1, 2, -3, 4}` are `2` and `4`, so the accumulator must end at `2 + 4 = 6`.
- **Actual:** `standalone Metal acc = 4.000000 (want 6.0)`

The observed value is exactly `0 + 4`: every qualifying iteration read the accumulator's **pre-loop** value `0`, and only the last store survived. That signature (stale base value re-read on every iteration, final store wins) indicates the load of `acc[0]` is being cached/hoisted across the loop-carried memory dependence introduced by the store in the same iteration.

## Discrimination matrix

All rows use the identical harness and single-thread dispatch; only the kernel shape changes. Rows 1–4 run on this machine with this exact harness; rows 5–6 are observed through our full compiler stack on the same machine.

| # | Kernel shape | Result | Verdict |
|---|---|---|---|
| 1 | **Unconditional** accumulate — same explicit `t = acc[0]; acc[0] = t + xs[i];` statements, `if` removed | `2.000000` (all four elements summed) | correct |
| 2 | **Conditional RMW** (kernel above): `if (xs[i] >= 0.0) { t = acc[0]; acc[0] = t + xs[i]; }` | `4.000000` | **wrong** (want 6.0) |
| 3 | Row 2 with the (empty) `else { }` branch removed | `4.000000` | wrong |
| 4 | Row 2 written as compound assignment `acc[0] += xs[i];` in MSL | `4.000000` | wrong |
| 5 | Same source logic executed on our **CPU** backend (identical IR-level program) | `6.000000` | correct |
| 6 | Accumulation emitted as a device **atomic** RMW (our production lowering for `arr[i] += v`) | correct | correct |

Two further shape perturbations of row 2 — a trivially-true condition, and the load of `acc[0]` hoisted out of the branch but still inside the loop — also return `4.000000` through our stack. The trigger is the combination **runtime loop + conditional branch + non-atomic RMW of the same memory location**, and it is insensitive to MSL micro-shape.

Note the important distinction between rows 4 and 6: hand-writing `+=` in MSL is **not** a workaround (row 4 miscompiles identically); only lowering to a genuine device atomic avoids the bug (row 6).

## Impact

Any MSL code that conditionally accumulates into an array/buffer element inside a runtime loop silently loses all but the last update: filtered histograms and per-bin scatter accumulation, contact/collision counters, linked-list and tree traversal accumulations, iterative solvers with conditional updates, sparse reductions. There is no diagnostic — the kernel compiles, runs, and returns plausible but wrong numbers, which makes this a silent numerical-corruption class of failure in production graphics and compute workloads. Compile-time-unrolled versions of the same accumulation are correct, so code that worked while testing with fixed sizes breaks as soon as trip counts become runtime values.

## Workarounds

- Emit a device atomic for the RMW (correct, but serializes and over-constrains where the algorithm is single-thread by construction).
- Fully unroll the loop so the dependence is not carried across a runtime backedge.
- Remove the branch where the algorithm allows an unconditional accumulation (row 1 is correct).

## Notes for triage

- Single thread, single threadgroup: the lost update is a **loop-carried dependence on one thread**, not a data race.
- The unconditional row of the matrix rules out a general problem with non-atomic device RMW or pointer aliasing; the failure is specific to the conditional form.
- Reproduction rate: 100% (deterministic, reproduces on every run).
